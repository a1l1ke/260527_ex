# Git Commit & Push 스킬

이 스킬은 현재 작업 디렉터리의 변경 사항을 **논리적 단위로 분리**하여 커밋하고,
원격 저장소에 푸시하는 전체 워크플로를 수행합니다.

---

## 커밋 메시지 컨벤션

모든 커밋은 아래 형식을 따릅니다:

```
<type>: <한글 메시지>
```

### 타입(type) 목록

| 타입       | 용도                                                   |
| ---------- | ------------------------------------------------------ |
| `feat`     | 새로운 기능 추가                                       |
| `fix`      | 버그 수정                                              |
| `docs`     | 문서만 변경 (README, 주석 등)                         |
| `style`    | 코드 의미 변화 없는 포맷 조정 (공백, 세미콜론 등)    |
| `refactor` | 기능 변경 없는 코드 재구성                            |
| `test`     | 테스트 코드 추가 또는 수정                            |
| `chore`    | 빌드 설정, 패키지 관리, 기타 잡무                     |
| `ci`       | CI/CD 파이프라인 설정 변경                            |
| `perf`     | 성능 개선                                              |
| `revert`   | 이전 커밋 되돌리기                                     |
| `build`    | 빌드 시스템 또는 외부 의존성 변경                     |

### 예시

```
feat: 사용자 인증 페이지 레이아웃 추가
fix: 모바일에서 메뉴 겹침 현상 수정
docs: AGENTS.md 에이전트 행동 지침 작성
style: 들여쓰기 및 공백 정리
chore: .gitignore에 node_modules 추가
```

## 에이전트 실행 워크플로

이 스킬을 활성화하면 에이전트는 아래 단계를 순서대로 수행합니다.

### Step 1 — 현재 상태 파악

```bash
git status
git diff --stat
```

변경된 파일 목록과 각 파일의 변경 내용을 확인합니다.
미추적(untracked) 파일, 수정된 파일, 삭제된 파일을 모두 파악합니다.

### Step 2 — 논리적 단위로 그룹화

변경 파일들을 아래 기준으로 **가능한 한 작은 그룹**으로 분류합니다:

- **기능 단위**: 동일한 기능에 속하는 파일들 (예: 로그인 UI + 로그인 로직)
- **파일 유형 단위**: 설정 파일, 문서, 스타일, 스크립트 등
- **독립성**: 각 커밋이 단독으로 이해 가능해야 함
- **원자성**: 한 커밋은 한 가지 이유(one reason to change)로만 변경

> ⚠️ 관련 없는 변경 사항을 하나의 커밋에 묶지 않습니다.

### Step 3 — 그룹별 Staged 커밋

각 그룹에 대해 아래를 반복합니다:

```bash
git add <관련 파일들>
git commit -m "<type>: <한글 메시지>"
```

파일 일부만 스테이징해야 할 경우 인터랙티브 모드를 활용합니다:

```bash
git add -p <파일>
```

### Step 4 — 커밋 이력 확인

```bash
git log --oneline -10
```

커밋이 의도한 대로 분리됐는지 검토합니다.

### Step 5 — 원격에 푸시

```bash
git push origin <현재 브랜치>
```

브랜치가 아직 원격에 없으면 upstream 설정과 함께 푸시합니다:

```bash
git push --set-upstream origin <현재 브랜치>
```

## 커밋 분리 판단 기준

에이전트는 다음 질문을 통해 커밋 분리 여부를 결정합니다:

1. **이 변경이 독립적으로 배포 가능한가?** → Yes이면 별도 커밋
2. **이 변경을 되돌릴 때 다른 변경에 영향을 주는가?** → Yes이면 분리
3. **PR 리뷰어가 이 커밋만 봤을 때 맥락을 이해할 수 있는가?** → No이면 분리 재검토
4. **한 타입(feat/fix/docs…)으로 설명되는가?** → 두 타입이 섞이면 분리

---

## 실행 예시

다음과 같은 변경 내역이 있을 때:

```
modified: index.html        ← 기능 변경
modified: style.css         ← 스타일 변경
new file: AGENTS.md         ← 문서 추가
modified: .gitignore        ← 설정 변경
```

에이전트는 아래 순서로 4개의 커밋을 생성합니다:

```bash
git add .gitignore
git commit -m "chore: .gitignore 설정 업데이트"

git add AGENTS.md
git commit -m "docs: 에이전트 행동 지침 AGENTS.md 추가"

git add style.css
git commit -m "style: 전체 레이아웃 CSS 스타일 정리"

git add index.html
git commit -m "feat: 메인 페이지 콘텐츠 구조 개선"

git push origin main
```

## 주의 사항

- **커밋 메시지**는 명령형이 아닌 자연스러운 한국어 서술형으로 작성합니다.
- `git push --force`는 절대 사용하지 않습니다. 단, 사용자가 명시적으로 요청한 경우는 예외.
- 스테이징 전에 항상 `git diff <파일>`로 변경 내용을 재확인합니다.
- 민감한 정보(API 키, 비밀번호, 토큰 등)가 포함된 파일은 커밋 전에 반드시 사용자에게 경고합니다.
- 이미 커밋된 내용은 수정하지 않습니다 (`--amend` 사용 금지, 단 사용자 명시 요청 제외).
